# PommeWeb handoff

For whoever continues this (Codex or a person): everything needed to pick
the browser port up where it stopped. Last updated 2026-11-23.

## Play it now

```sh
./play.sh            # builds dist/ if missing, starts relay + local server, opens Chrome
./play.sh --build    # rebuild the game first
```

Then **Multiplayer → Direct Connection → `127.0.0.1` → Join Server**.
The page is at http://127.0.0.1:8460. Chrome or Edge (WebGPU) only.

## Where things are

There are two folders. Code is **edited in the Pomme checkout** and
**published from this repo**.

| Path | What |
|---|---|
| `~/rust mc` | The Pomme checkout (upstream `PommeMC/Client`, base commit in `patches/BASE`). All Rust work happens here, uncommitted. **Do not commit to it or push it.** |
| `~/pomme-web-port` | This repo, `github.com/VKRTTY/PommeWeb`. Web-only code. |
| `web/` | Page JavaScript: `index.html`, `early.js`, `main.mjs` (loading screen), `webgpu.mjs` (GPU), `asset-storage.mjs` (IndexedDB), `transport.mjs` (server sockets), `audio.mjs`, `sw.js` (service worker). Edit these here. |
| `rust/` | Copies of the new browser-only Rust files, at their Pomme paths. **Generated by `sync.sh`; don't edit here.** |
| `patches/pomme.patch` | The port's edits to Pomme's own files. Generated by `sync.sh`. |
| `build.sh` | Builds `pomme-client` for wasm32 and writes `dist/`. |
| `sync.sh` | Copies the Rust side out of `~/rust mc` into `rust/` and `patches/`. Run before every commit. |
| `play.sh` | One-command play (above). |
| `scripts/browser-check.mjs` | Drives a real Chrome window over the DevTools protocol (see Testing). |
| `docs/progress.json` → `docs/progress.py` → `docs/progress.svg` | The README's progress map. Update the JSON as pieces land, then rerun the script. |
| `docs/screenshots/` | README screenshots. |

To set up a fresh Pomme checkout from this repo:

```sh
git clone https://github.com/PommeMC/Client pomme && cd pomme
git checkout "$(cat /path/to/PommeWeb/patches/BASE)"
git submodule update --init
cp -R /path/to/PommeWeb/rust/. .
git apply /path/to/PommeWeb/patches/pomme.patch
```

## Toolchain gotchas (read first)

- The repo pins `nightly-2026-08-21` (`rust-toolchain.toml`). On this Mac a
  **Homebrew `cargo` on PATH has no wasm32 std**, so put the rustup toolchain
  first: `export PATH="$HOME/.rustup/toolchains/nightly-2026-08-21-aarch64-apple-darwin/bin:$PATH"`.
- That nightly's `rust-lld` can't find `libLLVM.dylib`. Fix:
  `export DYLD_FALLBACK_LIBRARY_PATH="$HOME/.rustup/toolchains/nightly-2026-08-21-aarch64-apple-darwin/lib"`.
  `build.sh` and `play.sh` do both.
- `wasm-bindgen` CLI must be **0.2.121** (`cargo install wasm-bindgen-cli --version 0.2.121`),
  or put the binary at `tools/wasm-bindgen` (gitignored).
- Check commands:
  - browser: `cargo check -p pomme-client --target wasm32-unknown-unknown --no-default-features`
  - desktop (must keep compiling): `cargo check -p pomme-client`
- The relay's CSP forbids inline scripts and `fetch()` of `data:` URLs (images
  from `data:` are fine). Keep page scripts in files.

## How the port works

The game is Pomme's own Rust compiled to wasm32. Only OS-facing pieces have
browser versions, all behind `cfg(target_arch = "wasm32")`.

**Entry.** `pomme-client/src/lib.rs` `start(canvas)` (wasm-bindgen export, called by
`web/main.mjs`):
1. opens WebGPU (`renderer::rhi::backend::init`);
2. sets the data root to `/pomme`;
3. loads stored files (`web_fs::init`);
4. runs `run()` with `--username Player` (offline). The app is handed to the
   page's event loop with winit's `spawn_app` (`App::spawn`).

**Graphics.** `renderer/rhi/web/mod.rs` is a WebGPU backend with the same API
as `renderer/rhi/vulkan` (selected in `rhi/mod.rs`):
- GPU objects live in `web/webgpu.mjs`, and Rust holds integer ids.
- Push constants become a uniform at a placeholder `@group(9) @binding(0)`,
  renumbered per pipeline to the first free group and filled per draw from
  256-byte slots with dynamic offsets.
- `build_web_shaders.rs` converts SPIR-V to WGSL at build time and heads each
  shader with `// pomme-bindings g:b:kind[:dim]`. Bind group layouts are built
  lazily from that plus the actually bound resources (WebGPU layouts need
  sample types, view dimensions and read-only flags the RHI doesn't carry).
- Host buffers keep a CPU copy, for unaligned writes and texture uploads
  whose rows aren't 256-byte aligned (those use `writeTexture`).
- Readback buffers copy to MAP_READ staging after each frame, so results
  trail by a frame or more.
- Blits, mid-pass clears and texture clears are done with small render
  pipelines in `webgpu.mjs`.
- Pipelines with 4 bind groups *and* push constants can't work (WebGPU allows
  4 groups); that only affects distant terrain.

**Files.** `pomme-dirs/src/fs.rs` is `std::fs` on desktop and an in-memory
tree in the browser:
- The whole client goes through `pomme_dirs::fs` (also its `exists`,
  `is_dir`, `is_file` in place of `Path` methods). Never use `std::fs` or
  `Path::exists` directly in client code; on wasm they silently fail.
- `web_fs.rs` preloads the tree from IndexedDB (`asset-storage.mjs`), writes
  every change back, and fetches asset objects on first read.
- The installer (`pomme-install`, wasm path) downloads the client jar and all
  asset objects except `minecraft/sounds/*` and `minecraft/lang/*`, which are
  fetched on first read (`web::fetch_object`). Everything Mojang-hosted goes
  through the relay (`/relay/<host>/<path>`, via `sw.js` or `web::relay_url`).

**Threads.** A page has one thread:
- `tasks::Pump` runs the chunk-light worker and the chunk-occlusion walker on
  the game thread whenever their results are read.
- The chunk mesher runs queued jobs in `MeshDispatcher::drain_results`
  (`MeshQueue::run_here`), for 8 ms per frame, or 20 ms while there's a
  backlog. This was not yet rebuilt and tested when this file was written.
- `tasks::spawn_job` runs one-off thread work inline. `util::parallel_map`
  is sequential on wasm.
- Distant terrain has no thread (its jobs are dropped).

**Time.** `std::time::{Instant, SystemTime}` panic on wasm. The client uses
`web_time` everywhere; `time` has the `wasm-bindgen` feature. Never add
`std::thread::sleep`, `std::process::id`, blocking `recv` or
`reqwest::blocking` to a code path the browser runs.

**Networking.** `net/browser_transport.rs` + `web/transport.mjs` open a
WebSocket to the relay's `/connect/<host>/<port>`. `pomme-relay` must run
with `--allow-private-servers` to reach LAN or localhost servers.

**Loading screen.** It must look like vanilla's red Mojang Studios screen,
with **all text in the Minecraft font**, and stay up until the title menu is
ready (the user insisted on all of this):
- `web/main.mjs` draws it, with text from the game's `ascii.png` rendered
  on a canvas.
- The game's own splash (`splash_elements` in `renderer/mod.rs`) matches it.
- The game reports progress through `web_page.rs`
  (`pommeSplash`/`pommeReady` globals).
- The logo and font are cached in localStorage (`early.js` shows the logo
  before the first paint).
- Never ship Mojang's images in the repo; they come from the player's own
  download.

## State

Working in Chrome:
- the loading screens;
- the title menu with the panorama, and every menu screen with the blur;
- joining offline-mode servers;
- world rendering: terrain, sky, clouds, HUD, hand, player model.

Not done, in suggested order:

1. **Fast chunk loading.** Meshing is ~6 ms per column on one thread.
   - First, rebuild with the adaptive budget already in source and measure:
     the console logs `meshed N columns in T s`.
   - Then try `-C target-feature=+simd128` and fat LTO, which were never
     tested:
     ```sh
     export CARGO_TARGET_WASM32_UNKNOWN_UNKNOWN_RUSTFLAGS="-C target-feature=+simd128"
     export CARGO_PROFILE_RELEASE_LTO=fat
     export CARGO_PROFILE_RELEASE_CODEGEN_UNITS=1
     ```
   - The real fix is Web Workers.
     - Shared-memory wasm threads (atomics) are risky: std `Mutex` and
       crossbeam park via `memory.atomic.wait`, which **traps on the
       browser's main thread** under contention.
     - Safer: workers running their own wasm instance, loading the same
       render assets from IndexedDB, with snapshots and meshes passed as
       bytes.
2. **Microsoft sign-in.** Use the device-code flow (`pomme_auth::device_code_sign_in`;
   the browser already uses it in `ui/menu/account.rs`). `pomme-auth`'s
   `device_code.rs` still uses `tokio::time` (panics on wasm) and
   `lib.rs` uses `std::time::SystemTime`; switch both to `web_time` and a
   browser sleep. Then drop the forced offline `--username Player` in
   `start()` and the `not(wasm32)` in `UserData::for_launch`'s release flag
   (`lib.rs`). Accounts already persist in localStorage (`account.rs` `WebStore`).
3. **Distant terrain:** needs a worker (see 1), and its 4-group pipelines
   need push constants moved into a bind group.
4. **Singleplayer:** the integrated server (SteelMC) isn't built for wasm.
5. **Clipboard** (`ui/common.rs`): the browser clipboard API is async.
6. **Server resource packs** (`resources/packs/download.rs`) use blocking HTTP.
7. **Screenshots** (`copy_texture_to_buffer` with unaligned rows is skipped).

## Testing

`scripts/browser-check.mjs` opens a real Chrome window (headless Chrome has no
GPU on macOS) with a fresh profile, so every run is a first visit:

```sh
node scripts/browser-check.mjs http://127.0.0.1:8460/ 60 shot.png 15   # console + a shot every 15 s
node scripts/browser-check.mjs http://127.0.0.1:8460/ - outdir actions.json
```

`actions.json` is a list of steps:

| Step | What it does |
|---|---|
| `["waitfor", "globalThis.pommeIsReady", 400]` | waits until the title menu is up |
| `["wait", s]` | waits `s` seconds |
| `["shot", name]` | saves a screenshot as `name` |
| `["click", x, y]` | clicks, in CSS px of the 1280×800 window |
| `["key", "F5"]` | presses a key |
| `["hold", "w", s]` | holds a key for `s` seconds |
| `["type", "text"]` | types text |
| `["reload"]` | reloads the page |
| `["eval", "js"]` | runs JavaScript in the page and prints the result |

A first-visit install can take 1 to 3 minutes. Coordinates for the menus at
that window size:
- Multiplayer: (640, 360)
- Direct Connection: (640, 516)
- Options: (512, 540)

Local test server: SteelMC, built with
`cd "~/rust mc/third_party/SteelMC" && cargo build --release -p steel`.
`play.sh` runs it with an offline config. That server doesn't op offline
players, so `/gamemode` and `/tp` are refused.
